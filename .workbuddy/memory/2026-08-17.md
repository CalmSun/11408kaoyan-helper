## 修复：学习资料页文档页码/阅读进度不更新（Materials.vue）

### 根因（与 8/16 的误判不同）
- 8/16 误以为 `.ofv-viewport` 是 `overflow: visible`；实际 `node_modules/@open-file-viewer/core/dist/style.css` 中 `.ofv-viewport { overflow-y: auto }`，而 `.ofv-office-docx { overflow: visible }`，CSS 注释明确：“DOCX 纵向滚动统一由 viewport 承担”。
- docx 真实 DOM：`viewerContainer(.ofv-root/.doc-viewer-wrap)` > `.ofv-host` > `.ofv-viewport` > `panel(.ofv-panel.ofv-office.ofv-office-docx)` > `.ofv-docx-document` > `.ofv-docx-page-frame` > `section.ofv-docx`。
- **关键**：`.doc-viewer-wrap` 本身有 `overflow: auto`（Materials.vue:2151），因此运行时真正滚动的元素可能是 `.ofv-viewport` / `.ofv-panel` / 外层 `.doc-viewer-wrap` 三者之一。旧代码 `getDocumentScrollEl()` 取“第一个可滚动祖先”作为滚动监听对象 + IntersectionObserver 的 root，导致在多数情况下 root 与真实滚动元素错配 → 滚动监听与 observer 都不触发 → `docPage`/`docProgress` 永远停在恢复值（如 17）。这就是“翻页后页码不更新”的真正原因（8/16 的修复方向错了）。

### 修复方案（v3.4.8）
- 废弃 IntersectionObserver + 单元素滚动监听；改为 `window.addEventListener('scroll', handler, true)` 的 **capture 阶段**监听：`e.target` 即真实滚动元素，自动识别，不受 root 错配影响。
- 页码用几何法 `computeDocPageFromScroller(scroller)`：取包含视口竖直中心的页面块（中心落在间隙时取顶部已越过中心的最近页）。
- 保留 `setupDocMutationObserver`（frames 异步渲染后刷新）+ 新增 `setupDocResizeObserver`（缩放/布局变化重算页码）。
- `refreshDocPageNow()` 供无滚动事件场景（翻页/恢复/缩放）调用。
- 版本 3.4.7 → 3.4.8（package.json version + build output `release-v347`→`release-v348`）。

### 验证
- `vue-tsc --noEmit -p tsconfig.json` 对 Materials.vue 无报错（仅 main.ts / stores/index.ts 两个预存无关错误）。

## 热修复：v3.5.0 CI 构建失败（Materials.vue 模板编译错误）

### 报错
`[vite:vue] v-else/v-else-if has no adjacent v-if or v-else-if.` —— `vite build` 在 SFC 编译阶段失败（CI `electron:build:win` 触发的 release-v350 构建未产出）。

### 根因
v3.5.0 合并三套预览时，`.preview-container`（`v-if="currentFile"`，父节点）内部的三个兄弟分支 `doc-wrap` / `<img>` / `video-wrap` **全部写成了 `v-else-if`**。链首 `doc-wrap` 没有相邻兄弟 `v-if`（父级的 `v-if` 不能充当子级的 `v-if` 兄弟），故编译报错。

### 修复（提交 85c6f98）
- 将 `doc-wrap` 的 `v-else-if="isDocumentPreview(currentFile.ext)"` 改为 `v-if`，后续 `img` / `video-wrap` 保持 `v-else-if`，链合法。
- 本地 `npm run build`（vite build + tsc -p tsconfig.node.json）通过，退出码 0。
- 将 `v3.5.0` 标签移动到修复提交并 force-push，触发 CI 重新构建 release-v350。

### 教训
Vue 的 `v-if`/`v-else-if`/`v-else` 链只在同一父级下的**直接兄弟元素**间生效；重构时用独立 `v-else-if` 替换首个 `v-if` 分支是高频坑。vue-tsc 仅做类型检查，不会捕获此模板编译错误，必须以 `vite build` 验证。

## 修复：文档浏览获取当前页码 / 记录阅读进度（v3.5.1，Materials.vue）

### 用户反馈
"文档查看的浏览进度功能仍有问题"——v3.4.8 的 capture 滚动方案仍不更新页码、不记录进度。

### 根因（关键认知）
- 库的滚动容器是 `.ofv-viewport`（`overflow-y:auto`）；`.doc-viewer-wrap` 已 `overflow:hidden`，`.ofv-root/.ofv-host` 也 hidden，故只有 `.ofv-viewport` 可滚动。库会给 `viewerContainer`（即 `.doc-viewer-wrap`）加 `ofv-root` 类并按 `height:'100%'` 约束高度。
- 旧 `handleDocScrollCapture` 用 `e.target` 当滚动容器重算——在嵌套滚动 / 库实现差异下 `e.target` 不可靠，导致页码/进度不更新。**真正可靠的做法是 handler 忽略 `e.target`，始终从规范化滚动容器（`.ofv-viewport`）重算。**

### 修复（提交 153aa20）
1. `getDocumentScrollEl()` 优先直接取 `.ofv-viewport`（文档滚动容器），再兜底向上找/候选选择器。
2. `bindDocScrollCapture()` **直接监听真实滚动容器的 scroll 事件**（元素自身 scroll 必被本地监听捕获，最可靠）+ 保留 window 捕获兜底；`docScrollEl` 存引用以便解绑。
3. `handleDocScrollCapture()` 不再读 `e.target`，改为 `getDocumentScrollEl()` 重算页码+进度；加 rAF 节流避免每次滚动全量 `getBoundingClientRect`（仅 1 次/帧）。
4. MutationObserver / ResizeObserver 在滚动容器就绪后调 `bindDocScrollCapture()` 重新绑定直接监听。
5. `updateCustomToolbarDisplay()` 改从 `document` 查 `.ofv-custom-toolbar`（工具栏由库渲染，未必在 viewerContainer 直接子级）。
6. **新增 PDF 内部页码 best-effort 跟踪**：`onPdfFrameLoad`→`setupPdfPageTracking()` 给 iframe.contentWindow 绑 `hashchange` + 800ms 轮询读 `#page=N`，全部 try/catch（PDFium 常跨域 `chrome-extension://` 会抛 SecurityError，静默降级，仍保留自有工具栏翻页记录）。`unloadPdf`/`destroyPdf` 清理轮询。
7. 修正保存逻辑：`onDeactivated`/`handleBeforeUnload`/`watch` 对 PDF 改存 `{ pdfPage }`，Office/图片存 `{ docPage, scrollProgress }`（旧代码对 PDF 误存 `docPage`=1）。

### 验证
- `npm run build` 通过（退出码 0）；`vue-tsc --noEmit -p tsconfig.json` 仅余 2 个预存无关错误（main.ts / stores/index.ts），Materials.vue 零新增错误。
- 版本 3.5.0 → 3.5.1（release-v351）；标签 v3.5.1 已推送，CI 构建 release-v351。

### 注意
- PDF 跨域时内部页码无法回写（仅 record via 自有工具栏翻页），属已知限制；docx/office 现由直接 scroll 监听可靠跟踪。

## 修复三连：PDF 渲染仍失败（CMap 走 XHR 分支）+ 视频进度串号 + 文档竞态（v3.5.2 覆盖更新 #3）

### 用户反馈
1. CMap 本地化后 PDF 仍报「无法渲染该页面」；
2. 所有视频进度相同（应每个视频单独保留）；
3. 学习资料页大量 bug 及卡顿。

### 根因 1（PDF CMap，关键认知）
- pdf.js `fetchData()` 只对 **http(s)** URL 走 `fetch`；其余协议一律走 **XMLHttpRequest** 分支（`isValidFetchUrl` 正则 `/https?:/` 判定）。
- `kaoyan-assets://` 自定义协议 → XHR 分支 → **Electron 中 XHR 访问自定义协议不可靠**（而 fetch 自定义协议已被证明可用：open-file-viewer 的 `loadPdfData` 用原生 `fetch` 加载 `kaoyan-material://` 成功）。
- 修复：`cMapUrl`/`standardFontDataUrl` 改用**相对路径** `pdfjs/cmaps/` / `pdfjs/standard_fonts/`（基于 `document.baseURI` 解析）：
  - dev → `http://localhost:5173/pdfjs/cmaps/`（vite 服务 public，走 **fetch** 分支）✓
  - prod → `file://.../dist/renderer/pdfjs/cmaps/`（file:// XHR，Chromium 允许，`status===0` 分支）✓
- 附带：`cMapPacked: true` 显式声明；main.ts 的 kaoyan-assets 协议保留为备用通道并加 `Access-Control-Allow-Origin: *` 兜底。

### 根因 2（视频进度串号）
- `watch(currentFile)` 切换瞬间 `saveVideoProgress(nativeVideo.currentTime, duration)` 内部用 `currentFile.value.path`（**已指向新文件**）保存**旧视频的播放位置** → 新视频继承旧视频进度 → 逐个串号。
- 修复：`saveVideoProgress(time, dur, path?)` 增加显式 path 参数，切换场景传 `oldVal.path`；`onVideoEnded` 连播延迟加 `currentFile.path` 守卫（800ms 内手动切文件则取消连播）。

### 根因 3（卡顿/竞态）
- `saveProgress` 每次全量 JSON.parse + stringify localStorage → 加 `progressCache` 内存缓存（读零开销）+ **值未变跳过写盘**（`hasChange` 检查，排除 updatedAt）——文档滚动/视频节流保存不再反复序列化大对象。
- `openDocumentViewer` 异步竞态：快速连续切文件时旧 createViewer 可能覆盖新实例 → 加 `docViewerGen` 代际计数，destroy 时 +1，在途流程完成后代际不匹配则自毁。

## 修复 #4：PDF CMap 加载根因（kaoyan-assets+corsEnabled）+ 页码/进度 + 大文档卡片 + 热门评论置顶

### 根因 1（PDF 仍「无法渲染该页面」——上一版相对路径方案未根治）
- pdf.js `isValidFetchUrl` 只认 `http(s)`，其余协议一律走 XHR 分支（`fetchData`）。
- 上一版 cMapUrl 用相对路径 `pdfjs/cmaps/`：dev 走 vite http fetch（可用）；**prod 解析为 `file://`，XHR 访问 file:// 被 `webSecurity:true` 的 CORS 拦截 → CMap 加载失败 → 中文 PDF 报错**。这正是"仍然提示"的原因（用户测的是打包版）。
- 修复：cMapUrl/standardFontDataUrl 改用 `kaoyan-assets://pdfjs/cmaps/` 绝对 URL（dev/prod 行为一致，都走主线程 XHR 到自定义协议），并给 kaoyan-assets 协议在 `registerSchemesAsPrivileged` 加 **`corsEnabled: true`**（此前缺此权限，XHR 跨域读自定义协议失败）。
- 链路：cMapUrl 非 http(s) → pdf.js `useWorkerFetch=false` → worker 发 `FetchBinaryData` 给主线程 → 主线程 `DOMBinaryDataFactory._fetch` → `fetchData`（XHR 分支）→ XHR 到 kaoyan-assets（corsEnabled）成功。

### 根因 2（页码/进度）
- PDF 打开时 `initialPage` 与 `onLoad` 里 `restoreDocumentProgress→restoreDocPage` **双重 goToPage** → 滚动跳动/页码闪烁。修复：onLoad 里 PDF 走 initialPage 独家恢复，Office 走通用恢复。
- 库内置 `.ofv-pdf-page-navigator`/`.ofv-pdf-summary` 与页面级 `.doc-status-bar` **形成双导航**（注释称已隐藏但实际无 CSS 规则）。补 `display:none`（隐藏不影响 `input.value` 读取，页码源不变）。

### 根因 3（大文档卡片过长）
- grid/flex 子项 `min-height:auto` 被大文档撑高 → 卡片随页数变长。补 `.file-preview`/`.preview-container` 的 `min-height:0` + `overflow:hidden`，文档在 `.ofv-viewport` 内滚动。

## 修复 #8：PDF 黑屏根治（getTextContent 防御性包装）——库内 catch-all 是黑屏直接触发点

## 修复 #9：patch 函数与 ES module namespace 冲突回归（Cannot add property ... not extensible）

### 用户反馈
控制台报 `Cannot add property __ofvGetTextContentPatched, object is not extensible`，PDF 打开失败。

### 根因
- `import('pdfjs-dist/legacy/build/pdf.mjs')` 返回 ES module namespace：**不可扩展、属性只读**。
- 修复 #8 的 `pdfjs.__ofvGetTextContentPatched = true`（加属性）在严格模式下抛 Cannot add property；即使绕过，`pdfjs.getDocument = ...`（替换只读属性）同样抛 Cannot assign to read only property——两处都踩 namespace 限制。
- 另确认 `PDFPageProxy` 不在 pdfjs-dist 6.2.108 legacy 构建导出列表，无法直接拿 prototype。

### 修复（proxy 化，仅改 Materials.vue）
- `patchPdfGetTextContent(pdfjs)` 改为：基于 namespace 浅拷贝生成**可写代理对象** `{ ...pdfjs }`（GlobalWorkerOptions 仍指向原单例引用 → 库对 workerSrc 的赋值语义不变；version 等值拷贝），在代理上替换 getDocument 包装；文档就绪后经 doc.getPage(1) 定位 PDFPageProxy.prototype 包装 getTextContent；`WeakSet` 防重复包装（不再用对象属性标记）。调用点改为 `pdfjs: patchPdfGetTextContent(pdfjs)`（返回代理）。

### 验证
- node ESM 严格模式 + frozen namespace + class mock，12 项断言全 PASS（含复现旧错误、代理可扩展、GWO 同引用、正常透传/reject 降级/畸形兜底/二次 no-op/库 renderPage 等价流程 canvas 保留）。
- npm run build 通过；vue-tsc 仅 2 个预存无关错误；产物含降级文案、回环服务（main.js 127.0.0.1×5）、pdfjs 资源 169+16。

### 构建注意（坑）
- `mv dist` 备份后，增量 tsc（composite）因主进程源码未变而**不重建 dist/main** → 打包会缺 main.js。解决：`rm tsconfig.node.tsbuildinfo && npx tsc -p tsconfig.node.json` 强制重编译。

### 教训（重要）
- **Vite 动态 import 的 ES module namespace 不可扩展/属性只读**：要给第三方 ESM 模块"打补丁"，用浅拷贝代理对象（{ ...ns }）在其上替换属性，而不是改 namespace 本身；引用型导出（如 GlobalWorkerOptions 单例）在拷贝后仍同引用，语义不变。

## v3.6.2 四轮：侧栏 63→51vh 内部滚动 + 修复部分视频"一直跳开头"

### 用户反馈
- 侧栏列表高度 63vh→51vh，列表内容内部滚动。
- 部分视频"一直跳开头"（每次打开都从开头播/播放中回退）。

### "一直跳开头"根因（进度续播恶性循环）
自动续播在部分视频形成死循环：
1. DASH seek 到未缓冲远处 → MSE 缓冲不足 → 浏览器把 currentTime clamp/回退到 0~10s 小值；
2. onVideoSeeking/onVideoTick 把回退小值写进 localStorage → 覆盖原正常进度；
3. 下次打开按小值恢复 → 又 seek 失败 → 又覆盖 → 永远跳开头。

### 修复（三层防线，仅 BiliBiliPanel.vue）
1. saveBiliProgress 加 `time > 10` 阈值（与 loadBiliProgress 一致）——回退小值不落盘；
2. onVideoTick 前进保护：currentTime 大幅回退（< 上次保存 -5s）跳过保存；手动拖动走 onVideoSeeking 仍保存；
3. restoreBiliProgress 移除重复 loadStream（分 P 由 playVideo 统一恢复，消除二次加载竞态）+ seek 后 5s 校验未达目标则告警放弃、绝不二次 seek、原进度保留。

### 侧栏
- max-height 51vh；滚动从 side 自身下沉到 .bili-side-content（overflow-y:auto），UP 主卡片 sticky 不随列表滚动。

### 验证
- node 行为模拟 6 项断言全 PASS（回退不覆盖/正常保存/手动 seek 保存/阈值过滤/seek 校验）。
- build 通过；vue-tsc 仅 2 预存错误；产物含 51vh 与"放弃续播"特征。

### 教训
- **"续播跳开头"类 bug 的通用排查链：seek 失败(clamp) → 小值写回 → 下次按小值恢复 → 死循环**。防御：保存阈值 + 只前进不后退 + seek 后校验放弃。
- 进度恢复时分 P 切换应由入口统一处理（playVideo），不要在 restore 里重复 loadStream。

## v3.6.2 六轮：appendBuffer removed 报错根治 + 拖动重置根治（竞态防护）+ 播放卡片右移

### 用户反馈
1. 拖动进度条**仍**重置到开头，且报错：
   `视频流加载失败：Failed to execute 'appendBuffer' on 'SourceBuffer': This SourceBuffer has been removed from the parent media source.`
2. 播放卡片位置右移。

### appendBuffer removed 根因（竞态）
拖动超出缓冲 → seekDashIfNeeded 重启管道（stopDash 销毁旧 MSE + startDash 新建）：
- **旧 pumpTrack 竞态 append**：reader.read() resolve 后未查 abort 就 appendBuffer 到已移除 SourceBuffer → InvalidStateError → 显示错误页；
- **连续快速拖动并发重启**：pendingSeekSec 互相覆盖、旧管道覆盖新管道 → 播放头重置/错乱。

### 修复（全链路，仅 BiliBiliPanel.vue）
1. appendWithQuotaGuard / pumpTrack catch：abort、InvalidStateError、InvalidAccessError、AbortError **一律静默**（管道替换正常竞态，绝不显示"加载失败"）；
2. pumpTrack 循环：reader.read() 返回后/evict 前/append 后均查 abort；
3. seekDashIfNeeded 加 **dashRestartSeq 序列号**：await getPlayurlCached 后若序列过期 → 丢弃本次重启（防旧覆盖新）；
4. startDash 加 seekSecOverride 参数（显式传目标），pendingSeekSec 仅默认——并发不污染；
5. scheduleSeekAfterReady 绑定本管道 ms/sb，旧管道轮询 ms!==mediaSource 即退出；
6. Range 分支 HEAD/init/seg 任一失败 → try/catch 静默回退从头拉。

### 右移
- .bili-host padding-left:160px（内容中心右移约 80px，对齐 local 模式预览区视觉中心）；
- .bili-panel flex:1 → flex:0 1 auto（消除 flex-basis:0 覆盖 width）。

### 验证
- build 通过；vue-tsc 仅 2 预存错误；行为模拟 16 项 PASS（并发序列/append 静默分类/read 后 abort/Range 回退/管道绑定）。
- 产物特征：InvalidStateError/InvalidAccessError 防护、160px、flex:0 1 auto。

### 教训
- **"管道替换"类 MSE 竞态必须全链路静默**：appendBuffer 抛 InvalidStateError 不等于播放失败，是旧管道被新管道替换的正常现象——catch 中按错误名分类，管道替换类（InvalidState/InvalidAccess/Abort）静默，其余才显示。
- **并发异步重启必须用序列号**（++seq + 完成后比较），await 期间过期即丢弃——否则旧任务覆盖新状态。
