# Bilibili 播放器重构方案 - v3.6.2 Fix

## 🐛 核心问题诊断

### 1. **播放卡顿的根本原因**
- **错误时机**：在 `sourceopen` 事件中立即调用 `play()`，但此时 Video 元素尚未收到 `loadedmetadata` 事件
- **MSE 限制**：WebGL/MSE 编码的 Video 需要在 metadata loaded 后才能开始解码和播放
- **竞态条件**：`startDash` → `addSourceBuffer` → `pumpTrack` 异步拉流时，`play()` 可能过早触发

### 2. **播放失败的其他原因**
- **Codec 支持性误判**：`pickDashTrack`返回的轨道虽然通过了 `isTypeSupported` 检查，但在实际 append 时可能因为 fMP4 结构问题失败
- **音频轨道缺失**：部分视频只有视频轨道（无声），代码未正确处理
- **Seek 时机错误**：拖动进度条时的 seek 可能在源 buffer 未 ready 前就执行，导致位置重置

---

## ✅ 重构方案

### 核心改进点：

#### 1️⃣ **启动流程重排序**
```typescript
// ❌ 旧逻辑（错误）
sourceopen → addSourceBuffer → pumpTrack (拉流) → immediate play()
         ↑
     Metadata 未加载

// ✅ 新逻辑（正确）
sourceopen → addSourceBuffer → pumpTrack (拉流) → wait loadedmetadata → play() + seek
           ↑
       确保元数据已就绪
```

#### 2️⃣ **智能 Codec 回退机制**
- 优先选择 avc1（通用硬解最佳）
- hevc 降级（现代设备兼容性好）  
- any fallback（兼容性兜底）
- 实际播放失败时自动降级到下一优先级

#### 3️⃣ **缓冲管理优化**
- 主动清理历史区间（播放点前 10s 保留）
- 配额不足时激进释放（保留 2s 用于回拖）
- 同清晰度重启（绝不降清）

#### 4️⃣ **播放控制增强**
- 监听 `canplaythrough` 事件确保可流畅播放后才允许 autoplay
- 分离元数据加载与内容缓冲状态判断
- 增加 video.readyState >= 3 检查

## 📝 具体修改清单

### 文件：src/renderer/src/components/BiliBiliPanel.vue

#### 修改 1: startDash 函数重排（约第 1231-1298 行）
- 移除 sourceopen 中的 immediate play()
- 改用 canplaythrough 事件监听确保可流畅播放
- 增加 video.readyState >= 3 检查

#### 修改 2: pickDashTrack 优化（约第 1130-1175 行）
- 新增 encodeScore 函数明确 codec 优先级
- 精确匹配指定 Qn 时按支持性 + 带宽排序
- 无精确匹配时全局搜索最优 codec

#### 修改 3: pumpTrack 错误恢复（约第 1305-1451 行）
- read() 异常捕获后自动恢复续播
- 断流判断改为基于单轨道缓冲最远位置
- Range 定位失败时静默回退从头拉取

#### 修改 4: 新增播放状态监控（约第 1264 行后）
- 监听 canplaythrough 事件
- 检查 video.readyState >= 3（Have FutuerData）
- 延迟 play() 调用直到真正可流畅播放

#### 修改 5: 错误处理增强
- QuotaExceededError 触发激进清理 + 同清晰度重启
- InvalidStateError/A bortError 静默返回（正常竞态）
- 网络中断自动恢复（read() 异常触发 recoverDashStream）
